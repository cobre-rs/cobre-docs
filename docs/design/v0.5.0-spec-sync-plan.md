**Status**: drafted 2026-04, decisions fixed 2026-04-26.
**Trigger**: cobre v0.5.0 ships breaking changes that require rewrites — natural moment to revamp scope rather than patch in place.
**Outcome**: cobre-docs becomes a true methodology reference at `methodology.cobre-rs.dev`. Implementation content moves to a developer guide inside the main cobre repo's mdBook (working name: `developer-guide`, final naming pending cobre-book-side analysis).

> **Note on this document.** Transitional design artefact. Once the revamp lands, this file remains in `docs/design/` as a record of the decision but is no longer load-bearing. It is written in versioned/dated language _because it is itself a maintenance document_ — the rule "no versioning in methodology" applies to the published methodology book, not to internal planning notes.

## 0. The Lens

The single rule for every triage decision in this plan.

> **Methodology answers**: What does Cobre compute? Why this design and not the alternative? What does this knob mean and what is its trade-off?
>
> **Developer guide answers**: How is it implemented? What is the data layout? What is the API?

Worked example. Same topic written both ways:

### Methodology version

> When a cut is removed from and later re-added to the LP across SDDP iterations, its previous role in the warm-start basis is lost. Cobre predicts whether each re-introduced cut should start at LOWER (tight) or BASIC (slack) by looking at a _configurable moving window of recent activity_: a cut that has been binding repeatedly is likely to bind again, and starts LOWER; a cut that has been slack is likely to remain slack, and starts BASIC.
>
> The window length is the `basis_activity_window` configuration parameter (default 5, range 1..=31). It trades off responsiveness to changing trial-point geometry against stability of the prediction. The mechanism reduces simplex iterations per warm-started solve.

### Developer-guide version

> Each `CutMetadata` carries a 32-bit `active_window` field. Bit _i_ records whether the cut was binding _i_ iterations ago; bit 31 is a `SEED_BIT` marking fresh cuts. At iteration boundaries the classifier shifts left, ANDs against the mask derived from `basis_activity_window`, and counts set bits to drive the LOWER/BASIC promotion decision. Basis row status is fed to HiGHS via `Highs_setBasis`. See `cobre-sddp/src/basis_reconstruct.rs:86-119`.

Methodology **omits**: bit positions, struct fields, file paths, function names, FFI calls, language idioms, build flags, parallelism mechanics, internal error variants, wire formats.

Methodology **keeps**: the algorithmic idea, the guarantee, the configurable knob and what it controls, the trade-off, and the conditions under which the result holds.

Recursive test: if a section can be rewritten without naming a single Rust type, it belongs in methodology; if it cannot, it belongs in the developer guide.

## 1. Audience and Scope

### Methodology audience (`methodology.cobre-rs.dev`)

- Hydrothermal-planning analysts evaluating Cobre against alternatives
- Optimization researchers reading Cobre as one implementation of SDDP
- Modellers preparing cases (input semantics, configuration, output interpretation)
- Decision-makers reading executive-level rationale for design choices

They want to read _why we chose spectral over Cholesky for correlation factorisation_, not _how the cyclic Jacobi solver is implemented_.

### Developer-guide audience (cobre repo's mdBook)

- Developers extending or integrating with Cobre
- Maintainers triaging bugs against design intent
- Reviewers checking that an implementation matches the design

They want trait signatures, struct layouts, build profiles, FFI contracts, parallelism mechanics, and current-state descriptions of all the implementation machinery.

### Cross-linking

The two sites cross-link each other freely where it helps the reader. A methodology chapter on warm-start basis prediction may end with _"For the bit-window data structure and HiGHS plumbing, see developer-guide §X"_. A developer-guide chapter on `basis_reconstruct.rs` may open with _"Methodology: methodology.cobre-rs.dev/Part-IV/warm-start-basis-prediction"_. Cross-links are conveniences, not contracts.

## 2. Triage Rules

Every existing spec is classified into one of:

| Class        | Meaning                                                                                                                                                |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **KEEP**     | Methodology content; stays in cobre-docs (possibly with editorial trimming)                                                                            |
| **REHOME**   | Methodology content currently mislabelled in another section; move to its proper home (almost always under `math/`)                                    |
| **RELOCATE** | Pure implementation; move to cobre developer guide. May leave behind a one-paragraph "capability" statement absorbed into another methodology chapter. |
| **DELETE**   | Maintainer tooling that doesn't belong on either public site                                                                                           |
| **NEW**      | Methodology topics not currently covered in any spec; create from scratch                                                                              |

The lens (§0) is the only deciding criterion. Where in doubt, ask: _can this be rephrased without naming a Rust type?_ If yes, KEEP/REHOME/NEW; if no, RELOCATE.

**No decision-log artefact** is preserved on either site. Existing DEC-001..DEC-021 retire to git history. Where a rationale is genuinely useful to a reader, it surfaces inline as a plain "why" paragraph in the relevant chapter — never as a back-reference to a numbered decision.

## 5. Methodology Gaps Worth Filling Independent of v0.5.0

Five gaps in the methodology corpus pre-date v0.5.0 and would be worth filling regardless. Three become standalone NEW chapters under Part 4 (per §3.9); one is a section inside an existing math/ chapter; one is a reframing of an existing chapter. Each is sketched below with content list, knob coverage, and what is and is not promised. Detailed drafting happens during steps 4–6 of the migration path.

### 5.1 Warm-start basis prediction

**Lives in**: `math/warm-start-basis-prediction.md` (Part 4.7) — NEW.

**The gap**. The current corpus has no methodology coverage of how Cobre decides which cuts start LOWER (tight) and which start BASIC (slack) when warm-starting an LP whose cut set has changed between iterations. The mechanism has existed in code in some form since pre-v0.4; methodology has always been silent.

**What the chapter covers**:

- Problem statement: cut churn breaks the warm-start basis information that simplex would otherwise reuse.
- Idea: predict each re-introduced cut's role from past activity, not from re-solving. A cut that has been binding repeatedly is likely to bind again.
- Classifier: a configurable moving window of recent binding / non-binding observations.
- Knob: `basis_activity_window`, range 1..=31, default 5. Trade-off framed as responsiveness to changing trial-point geometry versus stability of the prediction.
- Guarantee and its limits: expected reduction in simplex iterations per warm-started solve. Methodology does not promise a specific speedup; it documents the mechanism and the conditions under which it helps.
- Closing line: cross-link to the developer guide for the bit-window data structure and HiGHS plumbing.

### 5.2 Determinism guarantees

**Lives in**: `math/determinism-guarantees.md` (Part 4.12) — NEW.

**The gap**. Cobre's determinism story is one of its most important methodology commitments and currently lives nowhere. Pieces are scattered across v0.4.3 release notes (LP determinism fix, sampler-count fix), v0.5.0 cementing (`f64` total-ordering discipline on hot paths), and the configuration reference (seed handling). No single chapter says what "deterministic" means in Cobre.

**What the chapter covers**:

- Definition: bit-identical results across (a) re-runs with the same seed, (b) MPI rank and thread configurations, (c) hardware within IEEE-754 conformance.
- Scope, enumerated: training (lower bound, cuts, trial points), simulation costs, scenario-tree generation.
- Methodology-level mechanisms (no implementation detail):
  - LP model is reloaded per scenario and per trial point so no internal solver state leaks across calls.
  - Comparisons on `f64` use a total ordering throughout hot paths — no NaN-driven non-determinism.
  - Sample-size-driven decisions use global counts, not per-rank counts.
  - Random seeds are derived deterministically across MPI ranks; no broadcast races.
- Out of scope, explicitly: wall-clock time, peak memory, compiler-optimisation-driven floating-point reorderings within a single hardware target.

### 5.3 Reproducibility and provenance commitments

**Lives in**: `math/reproducibility-and-provenance.md` (Part 4.13) — NEW.

**The gap**. Currently the only documentation of provenance is the output-file format (`metadata.json`, `stochastic_provenance.json`). There is no methodology framing of _what Cobre commits to recording so that any run can be re-derived_.

**What the chapter covers**:

- The commitment: any Cobre run can be re-derived from its recorded inputs and provenance.
- What is recorded (categories, not field names):
  - Input fingerprints (hashes of case files and configuration).
  - Stochastic-fitting metadata (PAR diagnostics, correlation source and method, opening-tree generation parameters).
  - Random-seed lineage: root seed and the rules by which per-stage and per-noise-group seeds are derived.
  - Solver and library identifiers (HiGHS, MPI library, ferrompi).
  - Execution topology — needed to evaluate the determinism claim of §5.2.
- What this enables: independent re-derivation of cuts and policy; audit trail for regulatory or scientific reporting; diff-of-runs analysis.
- What is explicitly not promised: bit-for-bit binary equality of output files (timestamps and schema-version metadata may legitimately vary), wall-clock metrics, system load.
- Pairs naturally with §5.2 (Part 4.12): determinism is the algorithmic property, provenance is the bookkeeping that makes it actionable.

### 5.4 Spectral correlation factorisation

**Lives in**: section inside `math/par-inflow-model.md` (Part 3.2). Not a standalone chapter.

**The gap**. Spectral decomposition replaced Cholesky for correlation factorisation in v0.4.0. The change is a methodology-level decision — it relaxes a precondition on the input correlation matrix and changes how degenerate hydros are handled — and is currently nowhere in the methodology corpus.

**What the section covers**:

- The problem: Cholesky factorisation requires the correlation matrix to be positive-definite. Estimated correlation matrices on small samples and from heterogeneous inflow series are often near-singular or rank-deficient.
- The choice: eigendecomposition with a symmetric matrix square root, clipping negative eigenvalues to zero.
- Why: the spectral form handles rank-deficient correlation matrices natively. The previously-needed degenerate-hydro filtering pass becomes unnecessary.
- The trade-off: slightly higher computational cost than Cholesky on well-conditioned matrices.
- The guarantee: cross-entity correlation structure is preserved down to the clipping threshold.

### 5.5 Inflow non-negativity hybrid formulation

**Lives in**: existing `math/inflow-nonnegativity.md` (Part 2.6). Not a new chapter; a reframing.

**The gap**. The current spec describes a reference `xi_h` formulation. The implementation hybridises Truncation clamping (PAR noise clamped before the LP is built) with Penalty slack columns (added inside the LP). The two are economically equivalent under matched penalty costs but differ in presentation. Methodology readers currently see one design; the code implements another.

**What the reframing does**:

- Present the production formulation (Truncation + Penalty hybrid) as the methodology baseline.
- State the equivalence with the reference `xi_h` form so readers familiar with the literature are not lost.
- Explain why the hybrid was chosen: clamping handles small noise excursions cheaply, slack handles large ones without making the LP infeasible.

## 8. Cross-Cutting Concerns

### 8.1 No decision artefacts on either site

The DEC log retires entirely. Existing DEC-001..DEC-021 do not move to the developer guide; they retire to git history. Where a decision's rationale matters to a reader, it is restated inline in the chapter that describes current behaviour, in plain language, with no DEC numbering.

### 8.2 No versioning in the methodology book

The methodology presents current Cobre as fact. No "since v0.5", no "added in v0.4.3", no "deprecated", no CHANGELOG-style annotations. Readers needing version history consult git or the cobre release notes. (This planning document versions itself — appropriate for transitional artefacts, not the rule for published chapters.)

### 8.3 No roadmap or deferred-features list in methodology

Forward-looking content (planned features, design reservations, GNL thermals, class-based Python API) belongs in the cobre book.

### 8.4 No inputs/outputs/configuration reference in methodology

Earlier drafts had a "Part 6 — Inputs and Outputs" and a "Part 7 — Computational Scale". Both fail the lens: they describe _how_ a user provides and consumes data, not _what Cobre computes and why_. Their methodology-relevant content (data requirements, knob meanings, output computations) is implicit in the modelling chapters that consume those inputs and produce those outputs. Pulling it into a separate Part duplicates content. The complete input/output/configuration reference lives in the developer guide.

### 8.5 Worked examples

Examples are pedagogical, not operational. Methodology carries the _modelling walkthrough_ — what the example illustrates about PAR, FCF, dispatch, coupling, etc. The runnable case files and "how to invoke `cobre run`" instructions live in the cobre book. `1dtoy` gets the most attention as the simplest case and best teaching vehicle; `4ree` follows. The existing `1dtoy.md` / `4ree.md` files in the cobre book remain there as the operational version; methodology versions are new files written to a different brief.

### 8.6 Diagrams

The diagram tooling (`diagrams/matplotlib/`, inline mermaid in mdBook, the design system at `docs/design/diagram-authoring.md`) is preserved. New methodology diagrams should be added as needed — value functions, scenario trees, FCF accumulation, multi-resolution aggregation, basis-window classifier illustration, etc. Existing HPC topology diagrams (D07, D08, D09) relocate with the rest of the HPC content. D02 (value function), D03 (scenario tree), D23 (PAR stored vs computed), D24 (LP column layout, if presenting column meaning rather than column index) stay. The `diagram-authoring.md` design-system doc itself stays in `docs/design/` as a maintainer guide.

### 8.7 Convention blockquote

Currently reproduced verbatim across HPC trait specs from `hpc/communicator-trait.md`. All those files RELOCATE to the developer guide. The blockquote travels with them; no methodology consequence.

### 8.8 Section-prefix discipline

The `§` / `SS` / plain split is retired in methodology. The new methodology corpus uses plain numbering (Part N, chapter M, section 1.2.3). The `§`/`SS` discipline survives only in relocated developer-guide files.

### 8.9 No "what changed" page

There is no transition document on either site. Users upgrading from v0.4 to v0.5 read the cobre `CHANGELOG.md` if they want history. The methodology book reads as if v0.5 is just current Cobre.

### 8.10 Cross-link convention

When a methodology chapter wants to point at implementation, use a single trailing line: _"For implementation, see cobre developer-guide §X."_ Avoid linking inside running prose. Keep the methodology readable as a standalone document.
